# ТЗ: Сайт регистрации брокеров на открытие апартамента

**Стек:** Nuxt 3 + PostgreSQL
**Автор ТЗ:** подготовлено для передачи в Claude Code
**Дата подготовки:** 2026-09-22

---

## 1. Контекст и цель

Клиент открывает первый апартамент в башне и приглашает брокеров на просмотр. Апартамент небольшой, поэтому гостей нужно развести по времени: группы по **15 человек** на **40-минутный слот**. Нужен публичный сайт-одностраничник со ссылкой для регистрации, куда брокер заходит, выбирает свободный слот и оставляет контактные данные. У клиента должна быть возможность посмотреть/выгрузить список записавшихся по каждому слоту.

Ключевое требование — **защита от переполнения слота**: как только в слоте набралось 15 записей, он должен блокироваться для новых регистраций (race condition должен быть исключён на уровне БД, не только на фронтенде).

---

## 2. Расписание и место проведения (известно от клиента)

- Дни: **вторник 13 октября, среда 14 октября, четверг 15 октября 2026**.
- Туры проходят **с 10:00 до 19:00** каждый день.
- Слоты начинаются **ровно в начале каждого часа**, длительность **40 минут** (20 минут — технический перерыв/пересменка групп): 10:00–10:40, 11:00–11:40, 12:00–12:40 … 18:00–18:40.
- Вместимость слота: **15 человек**.
- **Точка встречи:** лобби Al Salam Tower, Dubai Internet City, Дубай, ОАЭ.
- **Часовой пояс:** Asia/Dubai (GST, UTC+4, без перехода на летнее время) — определён по месту проведения, больше не открытый вопрос.

Итого **9 слотов в день × 3 дня = 27 слотов**, максимум **405 брокеров** за всё мероприятие.

Полный список слотов для сидирования в БД:

| День | Дата | Слоты (начало–конец) |
|---|---|---|
| Вторник | 2026-10-13 | 10:00–10:40, 11:00–11:40, 12:00–12:40, 13:00–13:40, 14:00–14:40, 15:00–15:40, 16:00–16:40, 17:00–17:40, 18:00–18:40 |
| Среда | 2026-10-14 | 10:00–10:40, 11:00–11:40, 12:00–12:40, 13:00–13:40, 14:00–14:40, 15:00–15:40, 16:00–16:40, 17:00–17:40, 18:00–18:40 |
| Четверг | 2026-10-15 | 10:00–10:40, 11:00–11:40, 12:00–12:40, 13:00–13:40, 14:00–14:40, 15:00–15:40, 16:00–16:40, 17:00–17:40, 18:00–18:40 |

> Даты и время не хардкодить в разметке — хранить в БД (через миграцию + seed-скрипт), чтобы для следующего мероприятия можно было просто пересеять таблицу без изменения кода. Все времена — по местному времени точки встречи (Asia/Dubai); хранить в БД либо как `time` без пояса + константа `EVENT_TIMEZONE=Asia/Dubai` в конфиге, либо явно с поясом — главное не смешивать подходы.

## 3. Функциональные требования

### 3.1 Публичная страница регистрации (`/`)

1. Шапка: название мероприятия, точка встречи — «Lobby of Al Salam Tower, Dubai Internet City», короткое описание (остальные тексты — плейсхолдеры, клиент пришлёт финальные).
2. Выбор дня — три вкладки/кнопки: Вт 13.10, Ср 14.10, Чт 15.10.
3. Под выбранным днём — сетка из 8 слотов. На каждой карточке слота:
   - время (например «11:00–11:40»);
   - количество свободных мест (например «Осталось 4 из 15»);
   - если мест 0 — карточка недоступна для выбора, помечена как «Мест нет» (не скрывать слот, а показывать как заполненный).
4. После выбора слота — форма регистрации:
   - Имя и фамилия (обязательно);
   - Телефон (обязательно);
   - Компания/агентство (обязательно);
   - Email (опционально) — *см. открытый вопрос 8.1, поля не подтверждены клиентом*.
5. Кнопка «Записаться». По сабмиту — серверная проверка вместимости (см. 3.3) и создание записи.
6. Экран подтверждения: «Вы записаны», дата, время слота, адрес, кнопка «Добавить в календарь» (генерация .ics — опционально, можно вынести в v2).
7. Адаптивная вёрстка mobile-first — брокеры в большинстве откроют ссылку с телефона.

### 3.2 Логика вместимости слота (критично)

- Проверка и резервирование места должны выполняться **атомарно на уровне БД**, чтобы два одновременных запроса не забронировали 16-е место в 15-местном слоте.
- Рекомендуемый паттерн (Postgres, без внешних блокировок):

```sql
-- в рамках одной транзакции
UPDATE event_slots
SET booked_count = booked_count + 1
WHERE id = $1 AND booked_count < capacity
RETURNING *;
-- если RETURNING ничего не вернул -> слот уже полон, откатить транзакцию, вернуть 409
```

  Если `UPDATE` вернул строку — в той же транзакции вставляется запись в `registrations` со ссылкой на `slot_id`. Если что-то в транзакции падает — весь блок откатывается, чтобы `booked_count` не «утёк» без реальной регистрации.

- Список слотов на фронтенде должен обновляться перед сабмитом (refetch остатка мест), чтобы пользователь не пытался забронировать заведомо занятый слот из закэшированного состояния страницы.
- Если слот заполнился прямо во время заполнения формы — сервер вернёт 409, фронт должен показать понятную ошибку («Это время только что заняли, выберите другое») и обновить сетку слотов.

### 3.3 Защита от дублей

- Предполагается (см. открытый вопрос 8.2), что один брокер может занять только один слот на всё мероприятие. Реализовать через уникальный индекс на `phone` среди активных (не отменённых) записей.
- При попытке повторной регистрации с тем же номером телефона — понятная ошибка с указанием, на какой слот он уже записан.

### 3.4 Админ-раздел (`/admin`)

- Простая защита доступа: логин через пароль, хранящийся в переменной окружения (`ADMIN_PASSWORD`), сессия по cookie. Без сложной системы ролей — админ один (клиент/Viktor).
- Таблица всех регистраций: имя, телефон, компания, email, день, слот, дата создания записи.
- Фильтр по дню и по слоту.
- Сводка по каждому слоту: занято/вместимость (например «12/15»).
- Кнопка экспорта в CSV (вся таблица или отфильтрованная выборка).
- Возможность отменить регистрацию (освобождает место — атомарно уменьшает `booked_count`).

### 3.5 Вне рамок MVP (не делать сейчас, но не мешать добавить потом)

- Отправка email/SMS-подтверждений брокеру.
- Waitlist (лист ожидания) на заполненные слоты.
- Мультиязычность интерфейса (сейчас один язык, но не хардкодить строки в компонентах вперемешку с логикой — держать в одном месте, чтобы потом было легко вынести в i18n).

## 4. Технологический стек

- **Frontend/SSR:** Nuxt 3 (Vue 3, TypeScript), Nitro server routes для API.
- **База данных:** PostgreSQL.
- **ORM:** Drizzle ORM (лёгкий, хорошо ложится на Nitro/serverless) — либо Prisma, если удобнее для реализации; выбор оставлен на усмотрение исполнителя, но должен быть один инструмент с миграциями как код.
- **Валидация:** Zod — общие схемы валидации переиспользовать между клиентом и сервером.
- **Стили:** Tailwind CSS (можно заменить на UnoCSS/обычный CSS — не принципиально).
- **Локально для разработки:** docker-compose с сервисом Postgres.

## 5. Модель данных

```
event_slots
  id            uuid primary key default gen_random_uuid()
  event_date    date not null
  start_time    time not null
  end_time      time not null
  capacity      integer not null default 15
  booked_count  integer not null default 0
  created_at    timestamptz not null default now()

  constraint booked_count_within_capacity check (booked_count <= capacity)
  unique (event_date, start_time)

registrations
  id            uuid primary key default gen_random_uuid()
  slot_id       uuid not null references event_slots(id)
  full_name     text not null
  phone         text not null
  company       text not null
  email         text
  status        text not null default 'confirmed'  -- 'confirmed' | 'cancelled'
  created_at    timestamptz not null default now()

  -- уникальность по телефону среди активных записей (частичный индекс)
  unique index on (phone) where status = 'confirmed'
```

Сидирование `event_slots` — согласно таблице в разделе 2 (27 строк).

## 6. API (Nitro server routes)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/slots` | Список слотов с датой, временем, `capacity`, `remaining = capacity - booked_count` |
| POST | `/api/registrations` | Тело: `{ slotId, fullName, phone, company, email? }`. Возвращает 201 + данные брони, либо 409 (слот полон / дубль по телефону), либо 400 (валидация) |
| GET | `/api/admin/registrations` | Защищено. Query-фильтры: `date`, `slotId`. Список записей |
| GET | `/api/admin/export.csv` | Защищено. CSV-выгрузка (с учётом текущих фильтров) |
| DELETE | `/api/admin/registrations/:id` | Защищено. Отмена записи, атомарно освобождает место в слоте |
| POST | `/api/admin/login` | Проверка пароля, установка сессионной cookie |

## 7. Нефункциональные требования

- **Часовой пояс:** мероприятие проходит в Дубае — все времена показывать в `Asia/Dubai` (GST, UTC+4). Хранить в конфиге `EVENT_TIMEZONE=Asia/Dubai`, не хардкодить в компонентах (пригодится, если следующее мероприятие будет в другом городе).
- **Производительность:** страница регистрации должна быстро грузиться на мобильной сети (SSR/минимум JS для первого экрана).
- **Доступность:** подписанные поля формы, видимый фокус, крупные тач-таргеты для карточек слотов (брокеры будут тыкать с телефона).
- **Логи:** логировать неудачные попытки бронирования (409/400) для последующей отладки нагрузки в день открытия.

## 8. Открытые вопросы к клиенту / допущения

Ниже — то, что ещё не подтверждено и требует уточнения до или во время разработки. Пока разработка не блокируется — приняты рабочие допущения (отмечены курсивом), которые можно поменять одной правкой конфига/схемы.

1. **Поля формы.** Допущение: имя, телефон, компания — обязательные; email — опциональный. Подтвердить у клиента, нужен ли email вообще.
2. **Один слот на брокера.** Допущение: один номер телефона = одна активная регистрация на всё мероприятие. Подтвердить, что это верно (а не «один слот на день»).
3. **Экспорт данных.** Допущение: таблица + CSV-экспорт прямо в админке сайта, без интеграции с Google Sheets/Excel. Если клиенту нужна автоматическая синхронизация в Google Sheets — это отдельная доработка (Google Sheets API), не входит в MVP.
4. ~~Часовой пояс / город мероприятия~~ — **закрыто**: Дубай, точка встречи — лобби Al Salam Tower, Dubai Internet City, пояс Asia/Dubai (GST, UTC+4).
5. **Тексты и брендинг.** Название проекта/апартамента, лого, цвета, точное описание тура — ожидаются от клиента отдельным брифом, в ТЗ заложены как плейсхолдеры (адрес встречи уже известен, см. раздел 2).
6. **Домен/хостинг.** Не указан — уточнить, где будет развёрнут сайт (Vercel, свой сервер, Docker) и есть ли уже домен.
7. **Уведомления брокеру** (email/SMS после регистрации) — не входит в MVP, см. раздел 3.5.
8. **Логистика от лобби до апартамента.** Если сама квартира находится не в лобби (например, нужно подняться на этаж или пройти к другому корпусу), стоит уточнить у клиента, нужна ли на странице/в подтверждении отдельная строка-инструкция «встречаемся в лобби, далее вас проводят» — сейчас это не заложено как отдельное поле, но текстово упомянуть можно в шапке/описании.

## 9. Критерии приёмки

- [ ] Публичная страница показывает три дня (13–15 октября) и для каждого — 8 слотов с корректным временем и остатком мест.
- [ ] Заполненный слот недоступен для выбора и явно помечен как «мест нет».
- [ ] Одновременная отправка формы двумя пользователями на последнее свободное место в слоте: ровно один получает подтверждение, второй — понятную ошибку 409.
- [ ] Повторная регистрация с тем же номером телефона отклоняется с понятным сообщением.
- [ ] Админ видит список всех регистраций, может фильтровать по дню/слоту и выгрузить CSV.
- [ ] Отмена записи админом освобождает место в слоте (счётчик уменьшается, слот снова доступен для брони).
- [ ] Страница корректно работает и выглядит на мобильном экране.
